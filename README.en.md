## Why it exists

When you ask an AI to build a page, vague phrasing gets you a coin flip: the model guesses the
control type and interaction rules, and you pay for wrong guesses in rework.

The same request, phrased two ways:

| | What you tell the AI | What you get |
|---|---|---|
| Before | "Make a dropdown to pick an owner" | A gamble: maybe a native `<select>`, missing clear/reset and keyboard support, with no rationale behind the choice |
| After | "Use a Select single dropdown for the owner: options are team members, single select, checkmark on selection, clear via ×, close on outside click or Esc" | Built to spec in one pass, form and interaction rules all in place |

This skill turns that translation into the AI's workflow: identify the request type, look up the
reference file, list candidates with a documented rationale, then output an executable spec.

## Install

```bash
# Interactive: detects installed agents (OpenCode / Claude Code / Cursor etc.), then installs
npx skills add shanchuann/better-web-controls

# Install only this skill, only for OpenCode
npx skills add shanchuann/better-web-controls --skill better-web-controls -a opencode

# Global install (available across projects)
npx skills add shanchuann/better-web-controls -g
```

Requires Node.js 22.20 or later. The skills CLI supports 75+ agents and writes the skill into each
agent's own directory (OpenCode: `.opencode/skills/`, global: `~/.config/opencode/skills/`). No
manual placement needed.

## Workflow

Once installed, the agent runs this flow on any web, page, or control request:

1. **Identify the request type** and route to the matching reference file (controls, layouts,
   interaction rules, fixes, charts)
2. **List candidates with rationale**: most controls have multiple forms (7 dropdown types,
   8 progress animations, 9 navbar patterns); output 2-3 candidates with fit notes, and ask the
   user when key information is missing
3. **Write a decision note**: candidate comparison, reasoning, and upgrade conditions go into
   `notes.md`, so the deliverable is reviewable
4. **Output the spec**: either a ready-to-use prompt (name, form, interaction rules in a fixed
   order) or a page generated directly from the spec

## Benchmark

9 real scenarios, 4 assertions each, comparing outputs with the skill versus without it (the
no-skill arm is blocked from reading the skill directory):

| Metric | With skill | Without skill | Delta |
|:---:|:---:|:---:|:---:|
| Assertions passed | **36 / 36 (100%)** | 31 / 36 (86.1%) | **+13.9pp** |

Per-scenario results:

| # | Scenario | With skill | Without skill | Failure without skill |
|:---:|---|:---:|:---:|---|
| 0 | Navbar | 4/4 | 3/4 | No candidate comparison or rationale |
| 1 | Page fixes | 4/4 | 4/4 | — |
| 2 | Carousel | 4/4 | 4/4 | — |
| 3 | Owner dropdown | 4/4 | 3/4 | No candidate comparison or rationale |
| 4 | Delete confirmation | 4/4 | 4/4 | — |
| 5 | Save feedback | 4/4 | 4/4 | — |
| 6 | Business report charts | 4/4 | 3/4 | No chart selection rationale |
| 7 | Empty states (two cases) | 4/4 | 3/4 | Wrong primary button on no-results state |
| 8 | Login page | 4/4 | 3/4 | No candidate comparison or rationale |

Two findings:

- **The selection process is the main gap**: 4 of the 5 failures are "no candidate comparison or
  rationale". Without the skill the model ships an implementation with an unreviewable process;
  with it, deliverables include candidate tables, reasoning, and upgrade conditions.
- **Implicit rules decide correctness**: on the empty-state scenario, the unskilled run built the
  no-results state as "message plus a big button" and added a "new customer" primary button that
  steers search-stranded users toward the wrong action. The skill's rule ("search: fix the
  keyword; filter: fix the conditions") avoids this.

Full report with per-assertion evidence:
[web-controls-workspace/iteration-2/benchmark.md](web-controls-workspace/iteration-2/benchmark.md)
