# 选型笔记：删除项目的确认交互

- 需求类型：交互反馈规则与时机（"删除要不要确认"）→ `rules.md` 二次确认一节；承载形式 → `controls.md` 弹窗、按钮
- 场景：后台管理的"删除项目"功能。删除后该项目的所有任务和文件全部消失，不可恢复。

## 一、判断依据（判断先于选择）

按 `rules.md` 决策线："后果可逆用撤销；轻微风险用长按或左滑；中等风险用气泡；严重后果用弹窗；不可逆且影响大用输入确认或独立确认页。"

逐项判断：

| 判断维度 | 本需求情况 | 结论 |
|---|---|---|
| 后果是否可逆 | 用户明确"不可恢复" | 排除撤销 Undo（撤销的前提是可恢复） |
| 后果严重程度 | 项目全部任务 + 全部文件一并删除，影响大 | 轻度确认（气泡、长按）不匹配，会导致事故 |
| 操作对象数量 | 删除的是单个项目，非批量 | 独立确认页/勾选确认过重 |
| 强度匹配 | 严重 + 不可逆 + 影响大 | 落在"输入确认"区间 |

## 二、候选对比

1. **弹窗确认 Modal**：蒙版阻断页面、要求明确选择，能完整说明删除后果（任务数、文件数）。是"严重后果"的标准答案；但确认只需一次点击，鼠标误点双击（点删除后紧跟点确认）仍可能造成事故。对"不可逆且影响大"防误触强度不足。
2. **输入文字确认 Type to Confirm（Modal 承载）**：要求用户完整输入项目名称后，删除按钮才启用。制造了与后果相称的操作成本，强制用户读后果说明，且从根本上防住误触与双击误操作。✅
3. **勾选确认 / 独立确认页 Select All to Delete**：后果逐条说明、全部勾选后执行，为"批量删除、最高风险"设计。本例只删一个项目，逐条勾选属于重度确认用于较重但非极端的场景，会过度打断用户。
4. **撤销 Undo**：不打断操作、提供反悔入口，体验最好；但需求明确不可恢复，前提不成立，排除。

## 三、最终选型

**输入文字确认 Type to Confirm，承载于居中 Modal 弹窗。**

理由：
- 决策线精确命中："不可逆且影响大"→ 输入确认。
- Modal 提供充足空间完整说明后果（"将永久删除 128 个任务、342 个文件，不可恢复"），满足二次确认"减少误触、说明后果、保留反悔机会"三项价值中的前两项（第三项因不可恢复天然缺失，由取消按钮承担）。
- Type to Confirm 补足 Modal 缺失的防误触强度：强度匹配原则下，这是"严重事项不采用轻度确认"的正确实现。

## 四、最终 Prompt（固定顺序：名称 → 场景/形式 → 操作规则）

> 做一个输入文字确认 Type to Confirm，承载于居中的 Modal 弹窗。触发：项目设置页危险区的"删除项目"红色面状按钮，点击后弹出 Modal，半透明蒙版阻断页面。内容：项目名称、后果清单（将永久删除该项目及全部任务与文件，逐项列数字并标注"不可恢复"）、输入框（placeholder"请输入项目名称以确认"）。操作规则：仅当输入与项目名称完全一致时，红色"永久删除"按钮才启用；确认后按钮进入加载态，完成后用右上角轻提示 Toast 反馈"项目已删除"，内容区切换为空状态。关闭方式：点击取消按钮、点击蒙版或按 Esc 关闭，关闭时清空输入并禁用按钮，焦点返回触发按钮。

## 五、实现要点核对

- 弹窗四要素齐全：类型（居中 Modal）、触发（删除项目按钮）、关闭（取消/蒙版/Esc）、内容（后果说明 + 输入框 + 双按钮）
- 按钮三步公式：删除为红色面状按钮（危险区唯一主操作）、取消为线状按钮；文字动词开头且说明结果（"永久删除"）
- 等待体验：删除请求期间按钮内循环同步 spinner（不确定进度，不编造百分比）
- 成功反馈：Toast 轻提示，右上角数秒自动消失
- 删除后：空状态说明结果，提供"重置演示"便于验收
- 可访问性：`role="dialog"` + `aria-modal`，打开时焦点移入输入框，Tab 焦点锁在弹窗内，Esc 关闭后焦点返回触发按钮
