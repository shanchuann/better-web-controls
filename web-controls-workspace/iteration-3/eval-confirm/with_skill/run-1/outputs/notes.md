# 选型笔记：删除项目的确认交互

## 需求分析

用户原话："后台管理里有'删除项目'功能，删除后所有任务和文件都没了，不可恢复，给删除按钮加合适的确认交互。"

关键判断依据（依据 `references/rules.md` 二次确认一节）：

- **后果是否可逆**：不可恢复 → 排除撤销与轻量方案。
- **影响范围**：整包删除（全部任务 + 全部文件 + 成员协作记录），影响大。
- **操作粒度**：单个项目删除，非批量。
- **场景**：后台管理桌面端（非移动端，排除触控类方案）。

参照核心公式"强度匹配：确认交互的打断程度应与操作后果的严重程度匹配。轻微事项重度确认会干扰用户，严重事项轻度确认会导致事故。"

## 候选对比（7 种二次确认，取 3 种候选）

| 候选 | 英文 | 适用场景（rules.md 原文） | 是否适配本需求 |
|---|---|---|---|
| 弹窗确认 Modal | Modal | 删除重要文档等严重后果 | 部分适配：能阻断页面、说明后果，但对"不可逆且整包删除"一些风险提升是多余的 |
| **输入文字确认** | **Type to Confirm** | 删除仓库、清空数据 | **适配：不可逆且影响大，制造额外操作成本阻止误操作** |
| 勾选确认（独立确认页） | Select All to Delete | 批量删除、最高风险 | 过重：本需求是单个项目删除，跳转独立确认页成本不值 |

其余候选（撤销 Undo、长按 Hold、左滑 Swipe、气泡 Popconfirm）均因后果不可逆或强度不足直接排除：不可恢复意味着没有撤销机会；长按/左滑针对防误触而非防高风险误决策；气泡属于中等风险。

## 最终选型

**输入文字确认 Type to Confirm，承载于居中 Modal 弹窗。**

理由：决策线明确"不可逆且影响大用输入确认或独立确认页"；单个项目删除选前者。原型参考"删除仓库"（GitHub 类同场景）。

## Prompt（按固定顺序：名称、场景/形式、操作规则）

"做一个删除项目二次确认：输入文字确认 Type to Confirm，承载于居中 Modal。点击列表中'删除项目'按钮后触发；弹窗内逐条列出删除后果（任务数、文件数、成员协作记录、不可恢复），要求输入与项目名称完全一致的文字后'确认删除'按钮才启用；输入不一致时在输入框下方给出错误提示；点击取消或按 Esc 关闭弹窗；确认后按钮内显示循环同步 spinner，完成后移除该行并弹出轻提示 Toast 告知已删除（不可恢复，故无撤销入口）。"

## 设计要点

- 弹窗四要素（controls.md）：类型 = 居中 Modal；触发 = 列表行删除按钮；关闭方式 = 取消按钮 / 右上关闭钮 / Esc（蒙版点击不关闭，防误触丢失后果说明）；内容 = 后果逐条清单 + 名称输入框 + 双按钮。
- 危险按钮在未满足条件时置灰而非隐藏，保持可见性（disabled 态样式区分）。
- 不校验大小写以外的花哨变化，要求 trim 后与项目名完全一致，防误触同时防删错对象。
- 确认后无撤销 Snackbar（rules.md 中"带操作的轻提示"对应可恢复删除），只用 02 级轻提示 Toast 告知成功，右上角 3 秒消失。
- 演示数据为 3 个项目，删除任意一行均可完整走通流程；全部删完后列表显示空状态。
